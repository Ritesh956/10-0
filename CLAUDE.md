# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Futbol: a football universe simulator (draft a squad → simulate a season → chase an unbeaten record → share the result), inspired by 38-0/FIFA Career Mode/Football Manager. Built as a pnpm/Turborepo monorepo. The original MVP architecture/database design lives in `plans/i-want-to-build-shiny-candy.md`; the active work is a phased **38-0 parity revamp** tracked in `plans/futbol-38-0-revamp-plan.md` (Phases 0-5 complete as of 2026-07-22: formations/settings foundation, draft-room polish, the animated season reveal, the January Transfer Window, the end-of-season narrative/awards, and persistence/trophies/history — read that doc's phase-by-phase completion notes before making structural changes; each phase's note records what was actually built vs. originally scoped).

## Commands

All commands run from the repo root unless noted. Package manager is **pnpm** (`packageManager` pinned in root `package.json`); Node >= 22.

```bash
pnpm install                     # install + link all workspace packages

pnpm build                       # turbo: build every package
pnpm test                        # turbo: run every test suite
pnpm typecheck                   # turbo: typecheck every package

pnpm --filter @futbol/engine test         # run one package's tests
pnpm --filter @futbol/engine test -- -t "determinism"   # single test (vitest -t filter)

pnpm --filter @futbol/api dev             # NestJS API, http://localhost:4000 (tsx watch)
pnpm --filter @futbol/sim-worker dev      # BullMQ worker (tsx watch)
pnpm --filter @futbol/web dev             # Vite dev server, http://localhost:5173

pnpm --filter @futbol/sim-lab exec tsx src/report.ts     # print engine calibration stats
```

Database (from `packages/db`):

```bash
pnpm prisma:migrate     # prisma migrate dev — creates + applies a migration from schema changes
pnpm prisma:deploy      # prisma migrate deploy — applies existing migrations (CI/prod)
pnpm prisma:generate    # regenerate Prisma Client after schema.prisma changes
pnpm seed               # tsx prisma/seed.ts — seeds the placeholder (fictional) reference dataset
pnpm seed:real          # tsx prisma/seed-real.ts — seeds the real top-5-leagues dataset (see below)
pnpm seed:managers      # tsx prisma/seed-managers.ts — seeds 100 real managers with hand-curated tactics (see below)
```

Each runnable package needs its own `.env` (copy from that package's `.env.example`): `packages/db`, `apps/api`, `apps/sim-worker` need `DATABASE_URL`; `apps/api`/`apps/sim-worker` also need `REDIS_URL`; `apps/api` needs `JWT_SECRET`. `apps/web` needs `VITE_API_URL`. `infra/docker-compose.yml` provides a local Postgres+Redis if you don't have your own.

Every package's `build`/`typecheck`/`test` scripts are standardized (`tsc -p tsconfig.json[--noEmit]`, `vitest run`), which is what makes the root `turbo run <script>` commands work uniformly — keep new packages consistent with this.

## Architecture

### Monorepo layout and dependency direction

```
packages/domain   -- shared types + zod schemas (Player, Squad, MatchEvent, MatchResult, jobs). Zero dependencies.
packages/engine   -- deterministic match simulator. Depends only on domain.
packages/db       -- Prisma schema/client, seed script. Depends on domain (for attribute shapes) and, as a devDependency, engine (seed script reuses its attribute generator).
packages/config   -- shared tsconfig base.
tools/sim-lab     -- statistical calibration harness for engine. Depends on engine (incl. its /testing subpath) and domain.
apps/api          -- NestJS REST API. Depends on domain, engine (types only), db.
apps/sim-worker   -- BullMQ consumer. Depends on domain, engine, db.
apps/web          -- React/Vite/Tailwind SPA. No workspace deps — talks to apps/api over plain REST via apps/web/src/api/client.ts (types hand-mirrored in apps/web/src/api/types.ts, not imported from @futbol/domain, since it's a separate ESM/bundler build target).
```

All Node packages are ESM (`"type": "module"`, `moduleResolution: NodeNext` from `packages/config/base.json`), so internal imports use explicit `.js` extensions. `apps/web` is the one exception: Vite/bundler resolution, extensionless imports, its own `tsconfig.json` (DOM lib, `jsx: react-jsx`, `moduleResolution: bundler`).

### The reference-catalog / world-state split (packages/db/prisma/schema.prisma)

This is the central data-modeling decision and shows up everywhere:

- **Reference catalog** (`Era`, `RefLeague`, `RefClub`, `RefClubSeason`, `RefPlayer`, `RefPlayerSeason`, ...): read-mostly, versioned. `RefPlayerSeason` is the draftable atom (a player's attributes in one specific season). Real-data licensing is an open question — see the architecture doc — so nothing outside this catalog hardcodes real identities.
- **Real dataset** (`prisma/seed-real.ts` + `prisma/data/real-top5-2012-2024.json.gz`): real players/clubs for the top-5 European leagues (Premier League, LaLiga, Serie A, Bundesliga, Ligue 1), seasons 2012-2024, sourced from [dcaribou/transfermarkt-datasets](https://github.com/dcaribou/transfermarkt-datasets) (real names/positions/appearances/market value/photo URLs — factual data, not scraped from a FIFA/EA-style ratings site). `overall`/`potential` are **computed by us** from a blend of market-value percentile, position-relative per-90 output, and involvement (minutes) — never copied from a third party's proprietary rating — then used as the `quality` seed for the engine's own `generateAttributes()` (`@futbol/engine/testing`), so attribute distributions stay consistent with `tools/sim-lab`'s calibration. `RefPlayer.photoUrl` hotlinks Transfermarkt's own image CDN directly (same trust level as the rest of the sourced data; no self-hosting/caching layer). Additive: seeded into the same `era-all-time` era as the fictional dataset, so both show up in the same league picker with no frontend change. ETL to regenerate the dataset lives in `tools/data-etl/` (see its README) — ratings formula tuning goes there, not in `seed-real.ts`. **Note on `createMany` + `skipDuplicates`**: it silently no-ops on rows that already exist, so a rerun that adds/changes a field (e.g. backfilling `photoUrl`) won't apply to previously-seeded rows — `seed-real.ts` follows up with an explicit per-row update pass for exactly this reason; keep that pattern for any future field additions to `RefPlayer`.
- **Player ratings mode** (`catalog.service.ts` `listPlayerSeasons`, `ratingsMode` filter: `"season" | "prime"`): "season" (default) returns each player exactly as they were in the drawn club-season. "prime" swaps in that player's own career-best (highest-`overall`) `RefPlayerSeason` — attributes/positions/overall/potential all come from the peak row, but `clubSeasonId`/club/season display context stays the drawn one, so the wheel still "found" them at that club while you draft the peak version of who they are. The substituted row's `id` is what actually gets drafted, so a player who peaked at a different club/season is fine — `DraftPage`'s existing `draftedIds` guard (keyed by `id`) already prevents drafting the same real person twice even if the wheel lands on them via two different club-seasons.
- **Managers** (`RefManager` + `prisma/seed-managers.ts`): 100 real, well-known managers, hand-curated (not ETL'd — small enough to author directly) with a real `name`/`nationality` and a tactical profile (`mentality`/`tempo`/`width`/`pressing`/`passingStyle`/`managerPhilosophy`) synthesized from well-documented public tactical analysis — same "real facts, our own derived rating" split as player `overall`, not copied from any FM/proprietary manager-attribute system. `WorldClub.refManagerId` is a **live FK** into `RefManager` (not copy-on-write like `WorldPlayer` — a manager's tactics don't evolve during a world's life, so there's nothing to snapshot). The user's own club gets whichever manager they draw via `POST /catalog/roll-manager` (optional, gated by the Setup "Managers" toggle; `refManagerId` rides along in the `draftFantasy` payload); both AI-fill paths below (`fillAiClubsFromLeague`/`fillAiClubs`) assign every AI-filled opponent club a random manager **unconditionally**, regardless of the human's own choice — tactical variety in the league only matters if all clubs have one, not just the user's — and both create all AI clubs **concurrently** (`Promise.all`, not a sequential `for`/`await` loop) — a ~20-club season means ~19 independent club instantiations, and running them one at a time against a remote DB was slow enough (each waiting on the previous) that `POST /worlds/:worldId/seasons` could look hung for a long time; keep this concurrent if you touch either method.
- **League-accurate AI-fill** (`SeasonsService.fillAiClubsFromLeague`, `createSeasonSchema`'s `leagueId`): the single-player path (everything driven from `apps/web`'s Setup/Draft/Season flow) fills the rest of the season with **exactly the chosen real league's own current clubs** — "current" meaning the most recent season year the dataset actually has for that league — instead of drawing from every real club-season across every era. That distinction matters: the original implementation only deduped by `RefClubSeason.id`, not by the underlying real club, so a league happily filled itself with the *same* handful of real clubs at 8-10 different historical seasons (e.g. ten different "Leicester City" rows) rather than twenty distinct clubs — a real bug, hit and fixed once. The league's size is never hardcoded — it's however many distinct `clubId`s that league's latest season year actually has in `RefClubSeason` (20 for the Premier League/LaLiga/Serie A, 18 for the Bundesliga/Ligue 1 in the current dataset), so the season's total club count is *derived*, not configured. If the user's own club came from a squad-first draft of a real club-season *in that same league*, that real club is excluded from the AI pool (otherwise it'd appear twice — once as the user, once as an AI duplicate of itself). The older size-based `fillAiClubs` (arbitrary real-club grab-bag across all eras/leagues, filtered only to `REAL_LEAGUE_COUNTRIES` — see below) still exists and is used when `leagueId` is omitted — currently just Multiplayer's fixed 2-club head-to-head (`MultiplayerPage.tsx`'s `createSeason(world.id, "Head-to-Head", { size: 2 })`), which has no natural "one league" to build around. Don't merge these two paths — they solve different problems.
- **World/save state** (`World`, `WorldClub`, `WorldPlayer`, `Season`, `Competition`, `Fixture`, `Match`, `MatchEvent`, `PlayerMatchStat`, ...): copy-on-write per save, everything scoped by `worldId`. Drafting copies `RefPlayerSeason` rows into new `WorldPlayer` rows with their own ids — **`WorldClub.lineup`/`.bench` (JSON `{position, playerId}[]`) must reference the new `WorldPlayer.id`, not the source `RefPlayerSeason.id`**. This bit a real bug once (see `apps/api/src/common/instantiate-world-club.ts` — it creates the `WorldClub` with an empty lineup first, creates all `WorldPlayer` rows, then updates the lineup/bench with the mapped ids). Any new code path that creates world players from ref data must follow the same two-phase pattern. Within that second phase, `WorldPlayer` rows are written via a single `createMany` + a follow-up `findMany` (scoped by the just-created `clubId`) to recover the generated ids for the lineup/bench mapping — **not** a `create` call per player in a loop; that per-row loop was the other half of the same slowness described above (~20 sequential round trips per club, ×19 clubs).

### Simulation engine contract (packages/engine)

`simulate(setup: MatchSetup, seed: bigint): MatchResult` is a **pure, deterministic function** — same inputs always produce the same output. All randomness goes through `createRng(seed)` (mulberry32); never `Math.random()`, never wall-clock time. Callers (currently only `apps/sim-worker`) generate a fresh random seed per match and persist `{setup, seed, engineVersion}` alongside the result for reproducibility/audit.

Internals worth knowing before touching `simulate.ts`: player attributes → `computePlayerQuality()` (per-dimension 0-1 scores) → `computeUnitRatings()` (aggregated per team, weighted by `POSITION_UNIT_WEIGHTS`) → tactics/home-advantage/weather modifiers applied once at kickoff → per-minute loop applies fatigue, momentum, then rolls chances/shots/cards/injuries/subs. Tuning constants live in `packages/engine/src/constants.ts` and are calibrated against realistic targets by `tools/sim-lab` (goal distribution, home-advantage, favorite-win-rate vs quality gap) — if you change a constant, rerun `pnpm --filter @futbol/sim-lab test` and `exec tsx src/report.ts` to confirm the distributions still look like real football.

**Tactics** (`strength.ts` `applyTactics()`): all five `Tactics` dimensions now have real mechanical effect. `mentality` shifts attack/defence balance (±18% at the extremes); `width` and `passingStyle` shift creation/attack/defence more modestly (±4-8%, same order of magnitude as the weather/home-advantage modifiers — deliberately kept well under mentality's swing so as not to destabilize calibration); `tempo`/`pressing` accelerate fatigue decay in `simulate.ts`'s `liveRatings()`. `managerPhilosophy` is **display-only** (shown in the UI, curated to already be narratively consistent with a given manager's mechanical fields) — it has no separate engine modifier, to avoid double-counting the same underlying tactical identity. Any change here needs the sim-lab recalibration step above; a contrasting-tactics sanity check (equal quality, only tactics differ) is a good way to confirm a new modifier has the intended directional effect before trusting the calibration numbers alone.

### Season simulation flow (api → queue → worker)

`apps/api`'s `SeasonsService.requestSimulation` marks the season `IN_PROGRESS` and enqueues a job (`SEASON_SIM_QUEUE` name + `SeasonSimJob` shape, both defined in `packages/domain/src/jobs.ts` so producer and consumer share the contract) onto BullMQ. `apps/sim-worker`'s `processSeasonSimJob` picks it up, rebuilds each fixture's `Squad` from persisted `WorldClub`/`WorldPlayer` rows (`build-squad.ts`), looks up each side's `WorldClub.refManager` and builds their `Tactics` from it (falling back to the shared `DEFAULT_TACTICS` for a manager-less club — see `tacticsForManager()`), calls `simulate()`, persists `Match`/`MatchEvent`/`PlayerMatchStat`, marks the `Fixture` completed, applies a light post-match fitness dip, and marks the `Season` completed once every fixture has a result. Morale/form progression *between* matches (independent of the January roster swap below) is still intentionally not implemented — don't add it ad hoc; note it in the revamp plan doc instead. `SeasonSimJob` also carries an optional `throughMatchday` (see "January Transfer Window" below) — when set, the worker's matchday loop stops early and leaves the rest of the fixtures `SCHEDULED`, so the `Season` stays `IN_PROGRESS` rather than `COMPLETED`; a later job with no `throughMatchday` picks up where it left off.

**Simulation throughput** (`processSeasonSimJob`, `simulateMatchday`, `simulateFixture`): clubs/players are loaded **once** up front (not re-fetched per fixture), and fixtures are simulated **matchday-by-matchday**, with every fixture in a matchday persisted **concurrently** (`Promise.all` across `simulateFixture` calls, each its own small `$transaction` of match+events+stats) — no club appears twice in the same matchday, so there's no write conflict. This replaced an original one-fixture-at-a-time loop with a fresh club/squad re-fetch per fixture, which took **15-20+ minutes** for a 380-fixture season against a remote/pooled Postgres (the same round-trip-latency trap already hit once in `fillAiClubs`/`instantiateWorldClub`). Fixture-status and post-match fitness updates are batched into **two raw `$executeRaw` `CASE`-expression UPDATEs per matchday** (`batchUpdateFixtureStatus`/`batchUpdateFitness`) instead of one `prisma.*.update()` call per fixture/player — for a 10-match matchday that's ~150-200 individual update calls collapsed into 2. **A real regression already hit and reverted once**: collapsing an *entire matchday's* matches into one big sequential `$transaction` of three bulk `createMany` calls (instead of one small transaction per match, run concurrently) measured **slower** overall (~74-84s vs ~24s for the same 380-fixture season) — it traded away the cross-match parallelism that was hiding per-round-trip latency, and fewer-but-serial statements lost to more-but-parallel ones. Don't re-introduce a single per-matchday mega-transaction for this reason. In practice, against Neon's shared free-tier compute, a 380-fixture season now takes roughly **60-90s** — measured across several structural variants (this one, a bigger Prisma connection pool, capped-concurrency updates), none of which moved that floor much further, so remaining time is dominated by remote round-trip latency itself, not application code.

**Animated frontend replay** (`apps/web/src/pages/SeasonPage.tsx`, `MatchPopupReel`): the backend always simulates a season as one instant batch job — there is no server-side streaming/pacing. "Watching a season unfold" is purely a client-side illusion: once `Season.status` flips to `COMPLETED`, `GET .../seasons/:seasonId/matches` (`SeasonsService.getMatchesWithEvents`) fetches every completed fixture's score + goal-by-goal breakdown in one shot (resolving `MatchEvent` `"goal"` payloads' `playerId`/`assistPlayerId` to names via `WorldPlayer.name` — a stored snapshot, so no ref-catalog join needed), and `SeasonPage` then reveals them one at a time through `MatchPopupReel` before moving on to standings/stats. **Replays are filtered to the user's own fixtures only** (`SeasonPage`'s `onlyMine()` helper, applied before every `MatchPopupReel` call — domestic league, Europe league phase, and each knockout round alike) — nobody wants to sit through all 380 league matches (or every other tie in a knockout round) to see their own results roll in; this cuts a full league replay from ~380 cards down to ~38. **Revised 2026-07-22** (to match 38-0.app's continuous ticker-style reveal, researched in `plans/38-0-app-research.md`): `MatchPopupReel` no longer shows one card at a time via `AnimatePresence mode="wait"` (exit-before-next-enters) — it now **accumulates** cards newest-first into a scrolling feed (nothing ever exits, so `AnimatePresence`/`forwardRef` aren't needed here anymore — that gotcha was real for the old implementation but doesn't apply to the current one), alongside a live `StatStrip` (W/D/L/Pts/GF/GA) that recomputes from the matches revealed so far via `lib/matchResult.ts`'s `accumulateRecord`. Card format (W/D/L badge, `GW<n>`, opponent + H/A, own-goals-only scorer line) is shared with `MatchLog.tsx` (the post-season full-log view) through `matchResult.ts`'s `summarizeForClub` — both components reframe a match from one club's perspective off the same helper rather than each computing win/draw/loss and goal-filtering independently. `MatchPopupReel` now takes a required `userClubId` prop for this. Per-match hold time is still based on goal count, not a flat interval. "Skip ahead" bypasses all of this immediately regardless of animation state. `SeasonsService.getTeamStats` aggregates `PlayerMatchStat` for the "your club's season" screen — **it must filter to the queried club's own `WorldPlayer` ids first**: a `Match`'s `playerStats` rows cover both sides' full squads, not just one club's, so skipping that filter silently folds the opponent's players into "your" squad totals (a real bug hit and fixed once — keep the filter if you touch this method).

**Post-season stats hub** (`SeasonPage.tsx`'s `"stats-hub"` phase, `CompetitionStatsPanel`): replaces what used to be a one-shot, dead-end "summary" screen. Standings, bracket, and stats for League and (if qualified) Champions League now live behind a persistent tab toggle (`statsTab`) the user can flip between freely and indefinitely, rather than only ever seeing whichever competition the linear pipeline happened to end on. Two new backend aggregations power this, both keyed by **competitionId** rather than seasonId so the same call shape covers the domestic league (one `Season` row) and the Champions League (a separate `Season` row per stage — league phase, QF, SF, Final — all sharing one `competitionId`): `SeasonsService.getCompetitionStats` (Golden Boot, MVP, and a top-10 scorers table, aggregated across **every club**, not just the user's — MVP requires a minimum match count, a quarter of whatever the most-used player logged, so a single standout cameo can't win it) and `getTeamStatsForCompetition` (the existing `getTeamStats` aggregation, generalized to roll up across every `Season` under a competition instead of just one). `runKnockoutRound`'s return value (not `champion`/`allTies` state read via closure) is what feeds the final cache/summary — see the note on stale closures below. The whole bundle is cached to `localStorage` per-`worldId` (`saveStatsHubCache`/`loadStatsHubCache`) once a run finishes, and restored directly (skipping the entire animated pipeline) if the user leaves `/season` and comes back, or reloads — "easy to navigate anytime unless you start a new run" falls out naturally, since a new draft always gets a new `worldId` and finds no cache entry. `DraftContext.worldId` itself is persisted to `localStorage` too (unlike the rest of that context's ephemeral draft state) for the same reason — otherwise a reload would strand the user on Setup with no way back to a world that already exists server-side.

**Long-lived async closures and stale state** (`SeasonPage.tsx`'s `runKnockoutRound`): this function recurses across many `await` points (poll, replay, pause, per round) and is invoked exactly once per season run from a specific render's closure — reading component state directly (e.g. `champion`, `allTies`) from *inside* it after enough awaited work has happened can silently return the value as it was at the moment the pipeline *started*, not its current value, because the running closure was never "upgraded" to a later render's version of that state. `runKnockoutRound` sidesteps this by threading the accumulated `ties` array through its own recursion parameter and returning `{ champion, ties }` directly, so the caller uses the actual returned data rather than reaching for state. Keep this pattern for any new data that a long-running pipeline function needs to hand back reliably.

**Loading feedback between pipeline stages** (`SeasonPage.tsx`'s `runSeasonPipeline`/`runKnockoutRound`): every stage transition after the domestic season (Europe league phase, each knockout round) does a real backend call (`startEuropeLeaguePhase`, `startEuropeKnockouts`, etc.) plus a `pollUntilCompleted` wait *immediately* after the user clicks a "Continue" button — and until this was fixed, `phase` didn't change during that wait, so the same stale result screen (with the same, now-inert "Continue" button) just sat there with zero visual feedback for however long the backend actually took, reading exactly like "Continue does nothing." Every such transition now sets `phase` to the shared `"simulating"` state (with a contextual `simulatingLabel`, e.g. "Simulating the Semi-Final…") *before* kicking off the next backend call, so there's always something visibly different on screen the instant a pause is skipped. Keep this pattern — set `"simulating"` + a label — for any new stage inserted into either pipeline function.

**One required press through the whole knockout stage**: "Continue to Knockouts" (shown once, after the Europe league-phase standings) is the *only* button in the entire Champions League knockout stage — QF → SF → Final → champion all auto-advance on their own afterward, with brief (2.2-3.2s) pauses but no `<Button>` of their own on the round-result or champion screens. This used to show a "Continue" button after every single knockout round (QF result, SF result, champion), which read as far more manual friction than it actually was (each pause auto-resolved after a few seconds regardless), so the buttons were removed outright rather than just relabeled. `SeasonPage.test.tsx` locks this in — it asserts no `/^continue/i` button exists at any of those three screens.
- **Pre-season projection consistency** (`DraftPage.tsx`'s `computePreseasonOdds`): `winPct`/`top4Pct`/`relegationPct`/`projectedFinish` all derive from one continuous expected-finish rank (via a logistic distribution around it), not four separately hand-tuned curves — those used to visibly disagree with each other (e.g. a squad "projected 7th" simultaneously showing ~40% to win the league). If you touch this, `DraftPage.odds.test.ts` locks in that exact regression scenario plus monotonicity across the full rating range — don't let it start failing.
- **Draft-wheel deadlock guard** (`DraftPage.tsx`'s `doSpin`): if a drawn club's entire player pool has nobody eligible for the slot(s) still open (checked the same way `sortedPlayerPool` checks eligibility — against `effectiveSlot` if one's targeted, else "fits *any* remaining slot"), `doSpin` silently redraws again on its own, excluding that club, without touching the user's redraw budget (`rerollsRemaining`/`useReroll` are untouched). This is the fix for a real deadlock: without it, a squad-first draw that fills 10/11 slots and then draws a club with zero players for the one remaining position — with zero redraws left — left the user with no possible action. Capped at `MAX_AUTO_REROLL_ATTEMPTS` (8) so a pathologically narrow filtered pool can't loop forever; past that it surfaces an error instead of hanging.

**European competition** (`apps/api/src/europe/`, `CompetitionType.CONTINENTAL`, the `KnockoutTie` model): the world is a single domestic league (20 clubs for the Premier League/LaLiga/Serie A, 18 for the Bundesliga/Ligue 1 — see league-accurate AI-fill above), not several real leagues feeding an actual 36-team UCL, so this is a deliberately scaled-down adaptation, not a literal replica — top 8 domestic finishers qualify (`EuropeService`'s `QUALIFIER_COUNT`), play a single round-robin "league phase" (`generateSingleRoundRobin`, added alongside `generateDoubleRoundRobin` in `apps/api/src/seasons/round-robin.ts`, both sharing the same circle-method first-leg logic), then an 8-team knockout bracket seeded 1v8/2v7/3v6/4v5: **QF → SF → Final**, two legs per tie except the single-match neutral-venue Final — deliberately no Round of 16, since 8 qualifiers leaves nothing to round down from. A `Season` can't be reused once `COMPLETED`, so each stage (league phase, QF, SF, Final) gets its own fresh `Season` row under one shared `Competition`; `EuropeService.advanceKnockouts` resolves the just-finished round's ties by aggregate score (falling back to a lightweight weighted-coin-flip penalty-shootout if level — not a full penalty-by-penalty simulation, that's out of scope) and generates the next round in the same call, reseeding by the original league-phase standings in bracket order. Every stage reuses `SeasonsService.requestSimulation` unchanged — the domestic queue/worker pipeline above has no idea a job belongs to a continental competition. `apps/sim-worker/src/process-season.ts` looks up each job's `Season.competition.type` once and sets `matchImportance` to `"cup"` (continental) or `"final"` (the Final specifically, resolved via `KnockoutTie.round`) instead of the domestic default `"league"`. The pre-season "European Nights" toggle in `SetupPage`/`DraftContext` **is** wired end-to-end as of Phase 0 (`World.settings.europeanNights`, see below) — `SeasonPage` reads it to decide whether to even call `/europe/status`; the backend's own qualification check is unconditional regardless, so the toggle is a frontend-only decision not to call/show Europe, matching 38-0's "Off = just the league" framing.

### January Transfer Window (`apps/api/src/january/`, Phase 3)

The domestic season is simulated in **two batches around a derived halfway pause, not two `Season` rows** — `SeasonSimJob` carries an optional `throughMatchday` (see above); `process-season.ts`'s pure `shouldSimulateMatchday()` just stops the matchday loop early. This was chosen over Europe's own multi-`Season`-per-`Competition` pattern specifically because a mid-season transfer needs to land inside one continuous set of standings — splitting into two Seasons would need every standings/stats query to merge across two `seasonId`s instead of one. `apps/web/src/pages/SeasonPage.tsx` computes the midpoint client-side from the already-generated fixture list (`Math.floor(maxMatchday / 2)`, never hardcoded) and only enters the January flow when `(world.settings?.januaryWindow ?? true) && userClub` and that midpoint is a real boundary.

`POST /worlds/:worldId/january/:seasonId/resolve` (`JanuaryService.resolveGamble`) finds the user's own weakest-rated occupied lineup slot, rolls a weighted POSITIVE/NEUTRAL/NEGATIVE event (35/40/25, `january.logic.ts`'s `pickEventType`), draws a replacement `RefPlayerSeason` for that position scoped to the world's era/league (biased toward an upgrade or downgrade per the event, falling back to the unbiased pool if the biased slice would be empty), instantiates a new `WorldPlayer` (same field-mapping as `instantiate-world-club.ts`), and patches the one lineup slot — all in one transaction, so the next `simulate` call picks up the new roster automatically (the worker re-reads `WorldClub`/`WorldPlayer` fresh every job; nothing is cached across jobs). The NEGATIVE event is a downgrade-replacement, not a "lose a player with no replacement" forced sale — the lineup must stay at 11 starters for `buildSquad()`/`simulate()` to run. `JanuaryEvent` (`schema.prisma`) is kept separate from `Transfer` — `Transfer` models one player moving between two `WorldClub`s, which doesn't fit a catalog-sourced arrival with no real "from club" in this world — and its `@@unique([seasonId, clubId])` is the idempotency guard against resolving the same club's window twice.

`apps/web/src/components/JanuaryWindow.tsx` reuses `DrawReel`/`SlotReel` (the same draft-room reel widget) for the CLUB × SEASON spin, following the exact "call the backend first, *then* set `target`/bump `spinToken`, then await the reel's own `onSettled`" pattern `DraftPage.tsx`'s manager-roll flow already established — never decide the winner client-side here, since `resolveGamble` already decided it.

### End-of-season narrative, awards, and squad tiers (Phase 4)

`apps/web/src/lib/seasonNarrative.ts` (`buildSeasonNarrative`, pure) assembles the results-screen "Season Story" block — verdict tag, per-unit word-tiers, a composition sentence (strongest/weakest unit), a finish-position flavor paragraph, January recap lines, a standout-player pundit quote, a manager closing line — entirely from data the stats hub already has cached (`SummaryDto.squad`/`squadOverall`, `TeamStatsDto`, `MatchSummaryDto[]`, `JanuaryResultDto`, `ManagerStatsDto.manager?.philosophy`). It's deliberately **not** given its own `CachedStatsHub` slot — it's cheap and pure, recomputed inline in `SeasonPage`'s render every time rather than persisted. The verdict tag recomputes a "projected finish" from the squad's *current* overall via `lib/preseasonOdds.ts`'s `computePreseasonOdds` (moved there from `DraftPage.tsx` in this phase specifically so a `lib/` file wouldn't need to import from `pages/` — apps/web's dependency direction is meant to run the other way) rather than persisting the pre-season projection anywhere, since it's a pure function of overall alone and always cheaply re-derivable.

`SeasonsService.getCompetitionStats` computes Golden Boot/MVP/**Playmaker** (top assister)/**Golden Glove** live on every read. Golden Glove is attributed to a **named goalkeeper**, not just the club — the engine's per-match `Squad` snapshot has no dedicated relational column, so `season-stats.logic.ts`'s `findGoalkeeperId()` parses the GK slot's `playerId` straight out of the JSON `Match.setup` for every clean-sheet match. `SeasonsService.getManagerStats` (`GET .../competitions/:competitionId/manager-stats`) is a **separate, domestic-only** aggregation (Clean Sheets/Longest Win Streak/Biggest Win/Highest-Scoring match, attributed to the club's `RefManager`) — walked in matchday order via the pure `computeManagerStats()` so "longest streak" is a genuine consecutive-run count, not just a tally.

`apps/web/src/lib/squadRatings.ts`'s `squadTierName()` maps a squad's overall to a flavor band (Galácticos → Minnows), surfaced on both the draft-complete screen and the results screen — a separate label scale from `seasonNarrative.ts`'s per-*unit* word-tiers (Elite → Shaky), which narrate one of the four tactical units rather than the whole XI.

### Persistence: trophies, awards, records, history (Phase 5)

Completing a run doesn't persist anything by itself — `SeasonPage.tsx` calls `POST /worlds/:worldId/seasons/:seasonId/finalize` (`SeasonsService.finalizeRun`) itself, right where it already calls `saveStatsHubCache`, specifically because **the frontend, not the worker**, is the only party that reliably knows a whole run (not just one `Season`) has actually finished — a `Competition` can span several `Season` rows (Europe's league-phase/QF/SF/Final), so a worker-side "on Season complete" hook would fire too early or not know which stage was the last one. `finalizeRun` evaluates the trophy catalog (`apps/api/src/seasons/trophy-evaluation.ts`'s pure `evaluateTrophies()`, keyed by `packages/domain/src/trophies.ts`'s shared `TrophyKey` enum — Invincible/Unbeaten are mutually exclusive, a perfect record earns the rarer one not both), and persists `Achievement`/`Award`/`WorldRecord` rows. All three models got `@@unique` constraints added in this phase specifically so `createMany({ skipDuplicates: true })` makes `finalizeRun` idempotent — safe to call twice (e.g. a stats-hub reload) without duplicate rows.

`apps/web/src/lib/trophies.ts` hand-mirrors `TrophyKey` as a plain string union (same zero-workspace-deps convention as `JanuaryEventType`) into a **display-only** catalog (name/description/icon/color) — the backend decides *what* was unlocked, this decides *how* to show it. `GET /worlds/history` (`WorldsService.getHistory` — note: registered **before** the `GET /worlds/:worldId` route in `worlds.controller.ts`, since Nest/Express match by registration order and a literal `history` path segment would otherwise be swallowed as a worldId) powers `/history`, reading `WorldRecord`'s `"points-total"` row and `Achievement` rows per world rather than re-deriving standings — a world whose run was never finalized just shows "In progress."

`apps/web/src/components/GuestPersistPrompt.tsx` is the peak-moment "don't lose this season" panel on the results screen — distinct from both the hard squad-confirm `GuestGateModal` and `SiteHeader`'s always-visible "Save your progress" header button, though all three ultimately call the same `useAuth().upgradeAccount`/`SaveProgressModal`, just at different moments.

### Dependency injection under `tsx watch`

`apps/api`'s `dev` script runs via `tsx watch`, which transpiles through esbuild — and esbuild does not emit `design:paramtypes` decorator metadata, confirmed by feeding esbuild's own transform API the same `emitDecoratorMetadata: true` tsconfig and observing zero `Reflect.metadata` calls in the output. NestJS's constructor injection relies on that metadata whenever a parameter's *type alone* is meant to resolve it, so a plain `constructor(private readonly foo: FooService)` silently resolves to `undefined` under `tsx watch` — every route throws "Cannot read properties of undefined" with no startup error to warn you (`pnpm --filter @futbol/api build && pnpm --filter @futbol/api start`, which goes through real `tsc`, works fine — that gap is what makes this easy to miss). The fix, applied to every controller/service in this codebase: give every constructor parameter an explicit `@Inject(FooService)` / `@Inject(TOKEN)` token, never rely on the bare type. Keep this pattern for any new controller/service constructor — it's the only thing that makes `pnpm --filter @futbol/api dev` actually work.

### Auth: guest-first

`POST /auth/guest` creates a `User` with just a `displayName` (`email`/`passwordHash` nullable, `isGuest: true`) and issues a JWT — no signup friction to start playing. `POST /auth/upgrade` (authenticated) attaches `email`/`passwordHash` to that *same* user row (`isGuest: false`), so a guest's worlds/history carry over rather than requiring a fresh account. `register`/`login` are the traditional email+password paths for users who already upgraded. Don't reintroduce a hard login gate in front of `apps/web`'s entry flow — username-only play is a deliberate product decision, not a placeholder.

Two auth gotchas already hit once, worth knowing before touching this code:
- `JwtModule.register({ secret: process.env.JWT_SECRET })` in `auth.module.ts` reads `process.env` at **module-evaluation time**, which is before `@nestjs/config`'s `ConfigModule.forRoot()` has loaded `.env`. `apps/api/src/main.ts` therefore does `import "dotenv/config"` as its literal first line — before importing `AppModule` — so env vars are populated before any static `.register()` calls run. Don't remove that import or reorder it after the `AppModule` import.
- CJS packages without a normal ESM interop shape (e.g. `bcryptjs`) need `import bcrypt from "bcryptjs"` (default import), not `import * as bcrypt from "bcryptjs"` — the latter compiles fine but `bcrypt.hash` is `undefined` at runtime under real ESM output.

JWT `expiresIn` is **24h** (`auth.module.ts`'s `signOptions`), not the original 1h — a real draft (11 spins, picking players, appointing a manager) can genuinely take long enough that a 1h guest token expired mid-draft, and since the app never proactively detects an expired-but-present token client-side, confirming the squad just failed late with a raw "Unauthorized" and no recovery path other than signing out and redrafting from scratch. `DraftPage.handleConfirmClick` only shows `GuestGateModal` when `!isAuthenticated`, which a stale-but-present token doesn't trigger — so if this bites again, widen that check rather than just bumping the expiry further.

### Validation

Every Nest controller uses a shared `ZodValidationPipe` (`apps/api/src/common/zod-validation.pipe.ts`) with per-route zod schemas colocated next to each module (`*.schemas.ts`) — there's no `class-validator`/DTO-decorator usage anywhere in this codebase; keep new endpoints consistent with the zod pattern.

### apps/web: routing, the draft flow, and the design system

`apps/web` has real client-side routing now (`react-router-dom`, wired in `App.tsx`): `/` (`LandingPage`), `/signin` (`AuthPage`), `/setup` (`SetupPage`), `/draft` (`DraftPage`), `/season` (`SeasonPage`), `/multiplayer` (`MultiplayerPage`), `/history` (`HistoryPage`, Phase 5 — linked from `SiteHeader` for signed-in users). Auth stays guest-first per above — landing and setup are browsable without a token; a JWT is only requested (via `GuestGateModal`) at the point an authenticated call is actually needed (confirming a drafted XI).

**Draft session state** lives in `apps/web/src/state/DraftContext.tsx` (config, in-progress `picks`, reroll budget, squad name, `worldId`) — client-side, and (aside from `worldId`) ephemeral, lost on a full page reload until `DraftPage`'s confirm step calls `createWorld` + `draftFantasy`. `worldId` itself is the one field persisted to `localStorage` (see the stats-hub note above) once a world actually exists server-side, so a reload after confirming a draft doesn't strand the user back on Setup. `SetupPage` writes the config; `DraftPage` reads/mutates picks; `SeasonPage` reads `worldId` to fetch the resulting world. There are **four** `FORMATION_POSITIONS`-shaped maps that must all stay in sync whenever a formation is added/changed, not just the two you'd guess from the web/api split: `apps/web/src/lib/formations.ts` (pitch-slot layout + position-group coloring), `apps/api/src/common/lineup.ts` (`buildLineup`'s greedy slot-fill), `packages/domain/src/tactics.ts`'s `formation` zod enum (gates `draftFantasySchema`/`draftClubSchema` validation — miss this one and a formation the web UI happily offers gets rejected server-side at draft-confirm time), and `packages/engine/src/testing/fixtures.ts`'s own copy (used only by engine/sim-lab test fixtures, typed against `@futbol/domain`'s `Formation` so a missing entry is at least caught at compile time). Hit and fixed once (2026-07-22, adding `4-1-2-1-2`/`4-2-2-2`): the domain-enum one is easy to miss since nothing fails until someone actually tries to submit a draft in the new formation.

`World.settings` (`Json?` column, added 2026-07-22 alongside the two formations above) persists the Setup "Advanced" toggles that used to be dead client-side state — `{ europeanNights: boolean, januaryWindow: boolean }`, defaulted server-side in `createWorldSchema` when omitted. `SeasonPage` reads `world.settings?.europeanNights` (defaulting to `true` for worlds created before this existed) to decide whether to call the Europe-qualification check at all; the backend's own `/europe/status` endpoint is unconditional and always computes real qualification regardless — the setting is a frontend-only decision not to call/show it, matching 38-0's "Off = just the league" framing. `januaryWindow` gates the January Transfer Window (Phase 3, see below) the same way — read by `SeasonPage`'s pipeline, defaulting to `true` for worlds created before either toggle existed.

**The spin-the-wheel draft** (`DrawReel`/`SlotReel` components + `DraftPage`): a client-side random pick from `listClubSeasons` filtered by league/era-year-range (not the backend's `/catalog/roll`, since that endpoint doesn't support the year-range narrowing the UI offers). The winner is decided **before** the reel animates (`doSpin` picks the club, *then* `SlotReel` spins a finite framer-motion-driven strip down to that exact pre-decided target — decelerate, then a spring settle with a slight overshoot — never a bare CSS loop cut off by an unrelated timer), and `doSpin`'s promise only resolves once `SlotReel` calls back `onSettled`, so the UI is never revealed before the animation actually lands on it. Gotcha already hit once building this: `SlotReel`'s spin-trigger `useEffect` must be gated purely by its dependency array (`[spinToken, spinning, winnerLabel]`) with no extra ref-based "already ran" guard — React 18 StrictMode's dev-only mount→cleanup→remount double-invoke will run the effect twice, and an extra guard that blocks the second run (thinking it's a duplicate) actually blocks the *only* run that doesn't get cancelled, hanging every spin forever, in production too, not just StrictMode. If a drawn club's pool has nobody eligible for the still-open slot(s), `doSpin` auto-rerolls on its own at no cost to the user's redraw budget — see "Draft-wheel deadlock guard" above. Gotcha already hit once on the drafting side: the same club-season can be drawn twice across separate spins, and since a club's placeholder-seed players are named generically ("Club Player 1", "Club Player 2", ...), it's easy to pick what *looks* like a duplicate. The real risk is picking the literal same `RefPlayerSeason.id` into two different slots — `draftFantasy`'s backend lookup (`findMany({ id: { in: ids } })`) silently collapses duplicate ids, so a squad with a true duplicate fails late with a generic "not found" error. `DraftPage` guards against this client-side (`draftedIds` set, disables/tags already-picked players in the pool) rather than relying on the backend to catch it. One pick per spin, by design — drawing a club shows its full squad, but choosing a player closes that draw and the next slot needs a fresh spin.

**Post-draft manager step**: once all 11 slots are filled and the Setup "Managers" toggle is on, `DraftPage` offers a real `/catalog/roll-manager` spin (`ManagerDto` — real name/nationality/philosophy/tactics, not the old fictional `MANAGER_NAMES` stub) before the final `draftFantasy` submission; declining ("No manager (classic)") leaves `refManagerId` unset and the club falls back to `DEFAULT_TACTICS` at simulation time.

**Position eligibility** (`POSITION_COMPATIBILITY` in `apps/web/src/lib/formations.ts`): a drafted player isn't checked against just the exact slot position — real positional versatility (CAM↔ST, CM↔CDM/CAM, LB↔LWB, CB↔LB/RB, etc.) is modeled as a compatibility graph, and `canPlayPosition()` is the single source of truth `DraftPage` uses to actually *block* an incompatible assignment (not just grey it out cosmetically) and to decide whether a player fits *any* remaining open slot, not only the one currently targeted — a player who fits none of the remaining slots is disabled and sinks to the bottom of the pool instead of failing later with a confusing error. This same graph is what the auto-reroll deadlock guard (above) checks against, so widening it (e.g. centre-backs now also covering LB/RB) directly reduces how often that guard needs to trigger at all.

**Real leagues only in the draft flow** (`REAL_LEAGUE_COUNTRIES` in `apps/web/src/lib/leagues.ts`): the backend still serves both the real top-5 dataset and the fictional placeholder dataset from the same era (see above), but `SetupPage`'s league picker and `DraftPage`'s club-season pool fetch both filter to the real top-5 countries only — fictional leagues/clubs are excluded from the whole draft flow at the frontend layer, not the API, so a new catalog endpoint consumer needs to apply the same filter itself if it should stay real-only. **`SetupPage`'s league picker no longer offers "All Leagues"** — `LeaguePicker` gained a `singleSelect` prop (hides the "All Leagues" button, makes selection exclusive by replacing `config.leagueIds` with a single-element array instead of toggling into it) that `SetupPage` passes; `SetupPage` also auto-selects the first real league once the list loads if none is picked yet, so `config.leagueIds` is never empty by the time a draft starts. This is required, not cosmetic: `fillAiClubsFromLeague` (see above) needs one concrete real league to build a season around, and an "all leagues" grab-bag has no single coherent "current top clubs" to fill with. `MultiplayerPage`'s own `LeaguePicker` usage is untouched — it still defaults to (and needs) the multi-select "All Leagues" mode for its roll-a-club flow, which has no per-league AI-fill concept at all.

**Squad naming and "(You)" identification**: `DraftContext.squadName` defaults to `""` rather than a generic "My Fantasy XI" placeholder — `DraftPage` computes `effectiveSquadName = squadName || user?.displayName || "My Fantasy XI"` (used for both the name-input's displayed value and the actual `draftFantasy` submission), so an untouched name defaults to the signed-in user's own display name instead of a generic label. Once in a season, `StandingsTable`, `KnockoutBracket`, and `CompetitionStatsPanel` all render an explicit `(You)` tag next to whichever row/tie/award matches `highlightClubId` — plain color-highlighting alone made it easy to miss your own row in a full 20-club table or an unrelated tie in the bracket.

**Player photos** (`RefPlayer.photoUrl` → `WorldPlayer.photoUrl`, copied at draft time by `instantiate-world-club.ts`): rendered directly as `<img>` in `PitchView`, `PlayerPickCard`, and `DraftedPlayerRow`, each with an `onError` handler that hides the broken image and falls back to the existing initials/rating badge — fictional players (`photoUrl: null`) hit that fallback by design, not as an error case.

**Design system** (revised — this replaced an earlier warm-charcoal/gold/notched-corner identity, deliberately moved closer to the genre's dark-mode-draft-game conventions rather than away from them): near-black neutral (`ink-*`) base, `paper` (neutral off-white) text, `mint` primary accent (actions, selection, primary CTAs — NOT literally named after its color, see below), `teal`/`plum`/`crimson` secondary accents, `amber` reserved narrowly for genuine trophy/celebration moments (Golden Boot, the Unbeaten ribbon, the Champions League winner panel) rather than as the primary color, `grass-*` reserved only for the literal pitch graphic. Shape language is rounded corners via the `.notch`/`.notch-sm` CSS utilities (`apps/web/src/styles/index.css`) — those class names are legacy (they originally drove an angular clip-path "ticket stub" shape) but were kept as-is rather than renamed, since redefining what they output let every component pick up the new rounded shape with zero per-component edits; don't be misled by the name, `.notch` means "rounded card," not "notched corner," in current code. Card/row borders lean flatter and lighter (`border` not `border-2`, `border-ink-800` not `border-ink-700`) than the old identity, relying more on background elevation and colored badges for visual interest. `Oswald` (display) + `Work Sans` (body) unchanged. Position-group colors (`apps/web/src/lib/positionColors.ts`, `GROUP_FILL`/`GROUP_TINT`/`GROUP_TEXT`/`GROUP_HALO`) are GK=`amber`, DEF=`teal`, MID=`mint`, ATT=`crimson` — deliberately a *different* four colors' worth of role-mapping than "primary/secondary/tertiary," so a defender's pitch marker is never visually confused with a primary CTA even though both can render in the same color family. Reuse these maps rather than inlining new color-per-position logic. New UI work in `apps/web` should stay within this token set.

**Motion** (`framer-motion`, the only animation engine in `apps/web` — no bare CSS `@keyframes` for anything beyond the two still-used `pop-in`/`mint-pulse` utilities in `tailwind.config.ts`): shared easing/spring presets and `Variants` live in `apps/web/src/lib/motion.ts` (`SPRING_SNAPPY`/`SPRING_BOUNCY`/`SPRING_SMOOTH`/`EASE_DECELERATE`, `staggerContainer`/`staggerItem`/`staggerItemBounce`, `fadeSlide`, `popIn`) — reach for these instead of inlining a new one-off transition. `apps/web/src/lib/confetti.ts` wraps `canvas-confetti` with brand-locked color presets (`fireQualificationBurst`/`fireChampionShower`/`fireTitleBurst`/`fireUnbeatenBurst`) gated behind `prefersReducedMotion()` (also in `lib/motion.ts`) — never free-hand a new celebration color or bypass that gate. `App.tsx` wraps the whole tree in `<MotionConfig reducedMotion="user">`, so any new `motion.*` element automatically respects the OS-level reduced-motion setting for free. Two gotchas worth knowing before adding a new animated component: (1) any custom component sitting directly inside an `AnimatePresence` must be `forwardRef` — hit once in the original `MatchPopupReel` (see "Animated frontend replay" above; that component no longer uses `AnimatePresence` at all after its 2026-07-22 rewrite into an accumulating feed, but the underlying gotcha is still real for any *other* component that mounts/unmounts children inside one); (2) a component extending native HTML attributes (`ButtonHTMLAttributes`, etc.) and spreading them onto a `motion.*` element needs `style`/`onDrag`/`onDragStart`/`onDragEnd`/`onAnimationStart`/`onAnimationEnd`/`onAnimationIteration`/`onTransitionEnd` omitted from that type — framer-motion redefines those names with incompatible signatures, which this repo's `exactOptionalPropertyTypes: true` tsconfig setting turns into a real type error, not just a warning (see the `MotionConflictingProps` omit-type in `ui/Button.tsx`/`ui/Chip.tsx`).

### Testing conventions

Vitest everywhere. Business logic that doesn't need Nest/Prisma/a browser is factored into plain, dependency-free functions specifically so it's unit-testable without mocking infrastructure: `apps/api/src/common/lineup.ts` (greedy formation-slot assignment), `apps/api/src/seasons/round-robin.ts` (circle-method fixture generation), `apps/sim-worker/src/build-squad.ts` (Prisma-row → domain-`Squad` reconstruction), `apps/api/src/january/january.logic.ts` (event-type weighting, weakest-slot detection, candidate-pool biasing), `apps/api/src/seasons/season-stats.logic.ts` (goalkeeper-from-`Match.setup` lookup, win-streak/biggest-win aggregation), `apps/api/src/seasons/trophy-evaluation.ts` (trophy-catalog conditions), `apps/web/src/lib/seasonNarrative.ts` (every narrative signal). `packages/engine/src/testing/` (exported via the `@futbol/engine/testing` subpath) provides deterministic squad/match-setup fixture generators reused by both the engine's own tests and `tools/sim-lab`. Prisma-coupled orchestration methods that just call 2-3 of the above and shape the result (`getCompetitionStats`, `getManagerStats`, `finalizeRun`, `getHistory`, ...) are deliberately **not** unit-tested directly in this codebase — the pure logic they call is what's tested; keep new service methods factored the same way rather than adding Prisma-mocking infrastructure.

**`apps/web` component tests** (`vite.config.ts`'s `test.environment: "jsdom"` + `test.setupFiles: ["./src/test-setup.ts"]`, `@testing-library/react`/`@testing-library/dom`): real, unmocked `framer-motion` animations run and complete correctly in these tests — jsdom's `requestAnimationFrame` always ticks, since jsdom has no concept of tab/page visibility to throttle it against, unlike a real backgrounded browser tab. This makes it possible (and worthwhile) to assert on actual animation-completion behavior — e.g. "the reel lands on the exact winner and calls `onSettled` exactly once" — rather than just shallow-rendering. `src/test-setup.ts` registers `@testing-library/react`'s `cleanup()` in an `afterEach` (required — without it, DOM from earlier tests in the same file accumulates and later `getByRole`/`getByText` queries start matching multiple stale elements) and stubs `window.matchMedia` (jsdom doesn't implement it, and `lib/motion.ts`'s `prefersReducedMotion()` calls it unconditionally). When mocking a whole module with `vi.mock`, remember it replaces *every* export — mocking `../lib/confetti` for one test but only naming two of its four exported functions will crash any component that imports one of the other two (a real mistake made once, see `SeasonPage.test.tsx`'s confetti mock).

**Live-browser-testing this app (not automated tests) hits the flip side of the jsdom note above**: an automated/agentic Browser-pane tab commonly reports `document.hidden = true` to the page, the same background-tab state a real browser uses to throttle `requestAnimationFrame` and slow `setTimeout`/`setInterval`. Since `App.tsx`'s route-transition wrapper (`<AnimatePresence mode="wait">` keyed on `location.pathname`) depends on an exit animation completing before the next route mounts, a client-side `navigate()` between top-level pages can update the URL but leave the DOM frozen on the outgoing page indefinitely in that environment — a real, hit-once gotcha (2026-07-22, live-verifying the Phase 0-2 draft/season revamp) that looks exactly like a broken route but is actually the tab-visibility throttle. Workaround: hard-load each page directly (bypasses the animated transition since there's no outgoing element to wait on) and, if a specific world/session needs to be attached to that fresh load, seed `localStorage`'s `futbol_token`/`futbol_user`/`futbol_world_id` keys directly rather than clicking through Setup → Draft → Season in one continuous session. In-page phase/state changes (e.g. within `SeasonPage` itself) aren't gated by this wrapper and animate/update normally regardless.
